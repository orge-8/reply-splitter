# reply-splitter —— 回复切分

用**可配置的规则切分**替换 MaiBot 宿主内置的回复分割器，让长回复拆成多条连发时
切在自然的位置，且**绝不切坏链接、代码块、颜文字**。

## 为什么需要它

宿主内置的分割器在 `config/bot_config.toml` 的 `[response_splitter]` 里，能调的旋钮只有这些：

| 配置项 | 默认 | 作用 |
|---|---|---|
| `enable` | `true` | 分割开关 |
| `max_length` | `512` | 单条最大字符数 |
| `max_sentence_num` | `8` | 单条最多几句 |
| `max_split_num` | `3` | 一次回复最多拆几条 |
| `enable_kaomoji_protection` | `false` | 颜文字保护 |
| `enable_overflow_return_all` | `false` | 句子太多时保留完整 |

全是**长度 / 句数级别的机械阈值**，没有任何语义或结构输入。所以它只能数标点、数字符，
不知道哪句该连、哪句该断，也无法识别一段文本里的链接和代码块 —— 这正是「切点生硬」
与「切坏结构」两个问题的共同根源，调参救不回来。

## 快速开始

### 1. 关闭宿主内置分割器（必做）

编辑 MaiBot 的 `config/bot_config.toml`：

```toml
[response_splitter]
enable = false
```

**不关会双重切分**：本插件把首段交回宿主发送链，宿主内置分割器会再把首段切一遍。

### 2. 安装插件

1. 将整个 `reply-splitter/` 目录复制到 MaiBot 安装目录的 `plugins/` 下。
2. 完整重启 MaiBot（**manifest 与配置变更热重载不生效**），观察加载日志是否出现
   `reply-splitter 已加载`。
3. 在 `[plugin]` 配置节确认 `enabled = true`（或 WebUI `http://127.0.0.1:8001` 启用）。

## 工作原理

```
回复模型产出回复
        ↓
maisaka.replyer.after_response    ← 只打「本条源自回复模型」的标记，不调模型
        ↓
send_service.after_build_message  ← 按规则切分：首段留在原消息里，其余登记待补发
        ↓
（宿主发送首段，保留引用与平台发送行为）
        ↓
send_service.after_send           ← 起后台任务，按顺序补发剩余段落
```

关键设计：

- **切分逻辑是纯函数**（`rs_splitter.py`），不依赖 `self.ctx`、不做 I/O、不用随机数，
  因此可脱机单测；`plugin.py` 只负责把配置喂进去、把结果发出去。
- **首段仍走宿主原始发送链**，引用、平台发送行为、历史同步都不受影响。
- **补发前必须做「实发校验」**：改写出站载荷这件事有一层陷阱 —— 只改到自己那份
  `kwargs` 副本也能让替换「看起来成功」，而宿主未必会重读它。此时若照旧补发，
  就变成「全文 + 后半段」，**同一内容讲两遍**。所以插件在 `send_service.after_send`
  阶段会先比对**宿主实际发出的正文**是首段还是全文：只有确认是首段才补发，
  判不准就一律放弃（日志留痕）。宁可漏切，绝不让内容重复。
- **重入保护**：补发期间同一聊天流的出站消息不再被切分，否则补发内容会被二次切分。
- **命令回执保护**：命令执行期间与其后 1 秒内不切分，避免把命令回执当成聊天回复。
- **任何异常都回退为原文直发**：切分失败不会吞掉回复，最坏情况就是回到没有插件的状态。

## 切分规则

### 强制分条边界：换行（最关键的一条）

**换行是回复模型表达「这句单独发一条」的唯一手段。** 因此本插件把换行当作
**不受长度预算约束的强制分条边界**：

```
整理曲库
晚点试播？
        ↓  切成 2 条
「整理曲库」 / 「晚点试播？」
```

两条例外：

- **代码块内部的换行不受影响。** 代码块本身就是多行的，若在这里分条会把代码块切开，
  保护区就形同虚设。优先级恒为 **保护区 > 强制分条边界**。
- **列表项之间的换行不分条**（`- xxx` / `1. xxx` 这类是排版，不是分条意图）。

改由配置项 `force_split_on_newline` 控制，默认开启。

> **关于「切得更碎」该怎么调**：关键**不是 `soft_max_length` 的大小，而是切点落在什么级别的边界上**。
> 同一个值在不同文本上效果可能相反，必须先看回复里有没有可用的干净边界：
>
> - **文里有标点**（`。` / `，`）→ 压小 `soft_max_length` 会让切点落到逗号上，
>   产出「今天主要整理一下曲库，」这种被切断的半句。此时**应该**靠模型换行来分条，
>   `soft_max_length` 退化为长段落安全网。
> - **文里只有空格、且每个空格分隔的都是完整小句**（某些模型被"不要用句号"之类的
>   提示词带成了这种风格）→ **空格本身就是小句边界**，压小 `soft_max_length` 是安全且有效的，
>   正是「水群感」的来源。
>
> 真机实测（181 字、纯空格分隔的回复）：
>
> | `soft_max_length` | 段数 | 长度分布 |
> |---|---|---|
> | 90 | 3 | `[80, 81, 18]` |
> | 60 | 4 | `[51, 52, 57, 18]` |
> | 40 | 5 | `[39, 24, 39, 37, 38]` |
> | 30 | 7 | `[27, 23, 28, 23, 26, 18, 30]` |
>
> 纯空格分隔风格下 `40` 左右是观感与条数的平衡点；`30` 更碎但会把诗意句和收尾句
> 拼在一起。**先确定回复的风格，再决定要不要压小这个值。**

### 保护区（解决「不切坏」）

下列片段先被标记为原子区间，**任何切点都不允许落在其内部**：

| 保护区 | 说明 |
|---|---|
| markdown 代码块 | ```` ``` ```` 围栏，含未闭合的 |
| 行内代码 | 反引号包裹 |
| 链接 | `http(s)://`、`ftp://`、`www.` 开头 |
| @提及 / #话题 | `@` 或 `#` 开头 |
| 括号对 | `（）()[]【】《》「」` 包裹的内容 |
| 颜文字 | 含制表符 / 几何图形 / 箭头 / emoji 等装饰符号的连续段 |

单段内含**比硬上限还长的链接**时，宁可让这一段超长也不断开链接。

### 切点优先级（解决「切点生硬」）

每个可落刀位置按优先级打分，在长度预算内挑最优切口，顺序为：

1. 段落分隔（空行）
2. 换行
3. 句末标点 `。！？!?…‥.`（含其后的收尾引号）
4. 分号 / 冒号 / 波浪号
5. 逗号 / 顿号
6. **汉字之间的空格** —— 中文排版里汉字之间不该有空格，出现了就说明是模型刻意打的
   停顿，属于子句边界
7. 普通空格（拉丁词之间、中英之间）—— 这类是正常排版，弱边界
8. 硬切（仅在前述都不可用时）

第 6 / 7 两档分开的意义：中英混排时，同一窗口内若同时存在两类空格，
会优先落在汉字间空格上，**英文短语因此更不容易被拆开**。
（注意这治不了"英文短语被拆"的根：那属于语义判断，规则层面无解 ——
只有当窗口内确实存在汉字间空格时才绕得过去。）

选刀策略是**宁可短一点，也要切口干净**：靠后窗口内若有句末标点级切点就取它；
否则放宽到整个窗口找句末标点级切点；都没有才退到逗号 / 空格级。

另外：不切开英文单词与数字（`2.8.1`、`bot_config.toml` 不会被断开）、不切开省略号、
过短的尾段会并回相邻段（不会甩出孤立的 `。`）。

## 配置

`config.toml` 由 Runner 在插件目录下自动生成，不要手工提交；写入时不能带 UTF-8 BOM。

### `[plugin]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `enabled` | `true` | 是否启用插件 |
| `config_version` | `1.0.0` | 配置版本，与插件版本同步 |

### `[splitter]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `enabled` | `true` | 是否启用规则切分 |
| `scope` | `replyer_only` | `replyer_only` 只切回复模型产出的回复；`all` 切所有出站文本 |
| `min_length` | `60` | 短于该长度的回复不切分 |
| `soft_max_length` | `180` | 单条目标长度 |
| `hard_max_length` | `480` | 单条长度上限（仅含不可分割原子时才允许超出） |
| `max_segments` | `6` | 一次回复最多切成几条 |
| `min_segment_length` | `12` | 短于该长度的段并回相邻段 |
| `force_split_on_newline` | `true` | 把换行当强制分条边界（详见下节） |
| `protect_code` | `true` | 保护代码块与行内代码 |
| `protect_url` | `true` | 保护链接 |
| `protect_brackets` | `true` | 保护括号对 |
| `protect_kaomoji` | `true` | 保护颜文字 |
| `typing` | `true` | 补发分段时沿用宿主的模拟打字等待 |
| `wait_for_pending_ms` | `8000` | 新消息到达时最多等待同流补发完成多少毫秒 |
| `diagnose_payload` | `false` | 打印出站载荷字段与正文预览，用于首次部署核对 |

### `[admin]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `admin_ids` | `[]` | 允许操作运行时开关的管理员 ID，兼容 `123456789` 与 `qq:123456789`；**留空表示所有人可用** |

## 配合宿主配置让回复更简短

**先说清边界：本插件不改变回复的总字数。** 它只决定同一段内容怎么切成几条发出去 ——
80 字切成 3 条还是那 80 字。所以「更简短」和「切得更碎」是两件正交的事：

| 目标 | 该动哪里 |
|---|---|
| 让内容**变短** | 宿主 `bot_config.toml` 的人设/提示词 + `model_config.toml` 的 replyer 生成参数 |
| 让节奏**变碎** | 本插件（配置见下） |

**顺序不能颠倒**：先用宿主配置把内容压下来，再用本插件把节奏调碎。
反过来做（LLM 吐 400 字、分段器切成 6 条长消息）只会更刷屏，不会更简短。

### 宿主侧要点

1. **默认配置里本来就写着「简短」** —— `[personality] reply_style` 默认含"风格平淡简短"，
   `[chat.reply_style] group_chat_prompt` / `private_chat_prompts` 默认含"回复尽量简短一些"。
   回复仍长时，先确认这三处有没有被改过，而不是急着加新提示词。
   诊断手段：`[debug] maisaka_prompt_preview_limit` + WebUI 的 Prompt 预览，看真实发出的 prompt。
2. **提示词要给具体数字和禁止项。** "尽量简短"这类模糊指令 LLM 服从度很低，
   改成"一次只说 1-2 句、不超过 30 字，不要分点、不要总结"才有效。
   **但"不要用句号收尾"这类要求会被过度执行**：真机实测模型会因此整段不用任何标点，
   变成"好 那再测一次 今天下午有点犯困 泡了杯茶继续整理曲库…"这种纯空格分隔，
   连逗号都不再出现，切分器可用的干净边界只剩空格一档。
   想让它分条，说"**想换口气就到下一行写**"比"不要用句号"更有效。
3. **`[model_task_config.replyer] max_tokens` 默认 4096**，对 QQ 闲聊几乎不构成约束。
   但注意两个坑：① `[[models]]` 里的 `max_tokens` 会**覆盖**任务级设置；
   ② 压太狠会硬截断，128 以下容易句子说一半被切断，建议只当兜底（300~500）。
4. **官方推荐与目标相冲**：文档建议 replyer 用 "pro 模型 + 思考模式" 以追求语言质量。
   思考模型会先内部推理一大段再输出有起承转合的长文 —— 这正是"像公告不像聊天"的来源。
   要短，这一层必须让步（换非思考模型）。
5. **两个内置但少用的超短机制**：`[personality] multiple_reply_style` +
   `multiple_probability`（官方示例直接给了"用1-2个字进行回复"，概率设 0.15~0.3 会让长度
   自然长短不均）；`[experimental.attention_drift] reaction_style`。

### 本插件的「更碎」推荐档

按回复风格二选一：

```toml
# A. 回复里带正常标点、靠换行分条（配合上面那段风格提示词）——长度只做安全网
[splitter]
min_length = 25
soft_max_length = 90
max_segments = 10
min_segment_length = 8
force_split_on_newline = true
```

> A 档下 `min_length` 不必压到 1：**含换行的回复不受 `min_length` 约束**
> （强制分条边界优先于"太短就不切"这条保护），所以「整理曲库↵晚点试播？」这种
> 十几字的短回复照样会被切开。

```toml
# B. 回复是「空格分隔的短句流」——空格即小句边界，可直接压小长度
[splitter]
min_length = 1
soft_max_length = 40
max_segments = 10
min_segment_length = 0
force_split_on_newline = true
```

判断依据很简单：**看 replyer 的原始输出里有没有标点**。
有标点就用 A（让模型换行决定断点）；全是空格就用 B（压小长度直接吃空格边界）。

### 一份可直接用的风格提示词

**先说一个容易踩的位置问题**：群聊与私聊是**两套独立提示词**——
`group_chat_prompt` 管群、`private_chat_prompts` 管私聊。只改一处，另一边不会有变化。
想全局生效改 `[personality] reply_style`。

把下面这段**追加**（不要替换）到 `[personality] reply_style`，
或按场景追加到 `private_chat_prompts` / `group_chat_prompt` 末尾：

```text
【发言风格】
你在闲聊，不是写文章，更不是写说明。
- 一次只说 1-2 句，总共不超过 30 字。对方明确要求你展开时才写长。
- 要接着说下一句，就直接换行——换行等于你按了一次发送键，会被单独发出去。
- 短句（一两个词、一句话）不带标点没关系，口语本来就这样。
- 但确实要写长时，就正常用逗号句号，不要用空格硬把句子断开。
- 不要罗列、不要分点、不要总结，不要出现"首先""其次""总的来说"这类词。
- 不要为了显得周到而补客套话，也不要复述对方已经说过的话。
- 允许只回一个词、一句没头没尾的接话，或者接个梗。
```

**为什么这么写（每条都对着一个真实失败模式）**：

| 这条要求 | 防的是什么 |
|---|---|
| 给具体字数 | "尽量简短"这类模糊指令 LLM 服从度很低 |
| **换行 = 发送键** | 配合本插件 `force_split_on_newline`，让模型能主动分条 |
| 短句可不带标点 | 承认口语事实，避免为了"守规矩"而硬加标点显得正式 |
| **长文要正常用标点** | ⚠ 直接修正上一版的坑：写"不要用句号收尾"会被**过度执行**成整段不用任何标点，产出 181 字纯空格长文，反而让切分器只剩空格一档可用 |
| 禁罗列 / 禁总结 | 干掉"助手腔"，那是"像播报不像聊天"的主因 |
| 允许只回一个词 | 明确授权"短到不合理"，否则模型不敢真的短 |

再配一条低成本、高收益的：`[personality] multiple_reply_style` +
`multiple_probability`（官方示例里就含"用1-2个字进行回复"），
概率设 `0.15~0.3` 会让长度**自然长短不均**——这本身就是真人感最强的来源，
比把所有回复统一压短更像人。

**改完怎么验证**：看日志里 `[言语] Maisaka 回复器生成成功 文本='...'` 那一行，
对照三件事——① 长度有没有降下来 ② 有没有出现换行 ③ 要写长时标点是否正常。
开 `[debug] show_maisaka_thinking = true` 还能看到模型自己的推理，
直接判断新要求有没有被它接受进去。

### 改提示词该走哪条路（四条路，只有一条首选）

`maisaka_replyer.prompt` 是 replyer 的提示词模板，实际内容就是**模板 + 占位符**：

```
{identity}
现在请你读读之前的聊天记录，把握当前的话题，然后给出日常且口语化的回复，
{reply_style}                                    ← 由 [personality] reply_style 填充
你可以参考【回复信息参考】中的信息，但是视情况而定，不用完全遵守。
{group_chat_attention_block}
{replyer_output_instruction}                     ← 输出格式契约，在最后
```

| 路径 | 升级会被覆盖？ | 作用域 | 建议 |
|---|---|---|---|
| `[personality] reply_style` | 否（配置迁移保留用户值） | 全局 | ✅ **首选** —— 它就是模板里 `{reply_style}` 占位符的填充源，位置本来就是留给风格要求的 |
| `[chat.reply_style] group_chat_prompt` / `private_chat_prompts` | 否 | 分场景 | ✅ 群/私聊需要不同语气时用 |
| `[[chat.reply_style.chat_prompts]]` | 否 | 单个聊天 | ✅ 只调某个群时用 |
| WebUI 的 Prompt 编辑（覆盖 `prompts/zh-CN/maisaka_replyer.prompt`） | 否，覆盖存 `data/custom_prompts/` | **全局，且失去上游模板更新** | ⚠️ 只在必须改模板结构（换占位符位置）时用 |
| **直接编辑 `prompts/` 下的文件本体** | **是，被覆盖或产生冲突** | 全局 | ❌ 不要 |

**为什么不建议覆盖模板来加风格要求**：

1. **模板里本来就有位置。** `{reply_style}` 就在"日常且口语化的回复"这句之后 ——
   这正是风格要求该待的地方。覆盖整个模板属于绕远路。
2. **"加在文件末尾"是最差的位置。** 末尾是 `{replyer_output_instruction}`，
   那是**输出格式契约**；风格要求压在它后面既容易被忽略，也可能干扰格式遵守。
3. **覆盖模板会让你收不到上游的模板改进。** 这些模板在持续更新
   （2026 年 5/6/7/9 月都有改动），一旦覆盖就得手动 diff 才能跟上。
   而 `reply_style` 走配置迁移，升级时自动保留用户值、只补新增字段。
4. **作用域失控。** 覆盖模板影响**所有**聊天流，无法按群差异化。

**如果确实需要覆盖模板**：别改文件本体，走 WebUI 的 Prompt 编辑入口
（存到 `data/custom_prompts/`，可版本回退、会校验 placeholder 完整性）。
用 `GET /api/webui/config/prompts` 可以查看当前有没有被覆盖过。

## 命令

| 命令 | 说明 |
|---|---|
| `/split` | 查看当前开关状态 |
| `/split on` | 开启（仅本次运行有效，不回写配置） |
| `/split off` | 关闭（仅本次运行有效，不回写配置） |

命令仅管理员可用，**拒绝时静默**（不发任何消息，只在日志留痕）。
未配置 `admin_ids` 时全部允许。

## 权限与能力

manifest `capabilities` 声明：`send.text`

本插件不调用模型、不访问数据库、不发起网络请求。改动 capabilities 后**必须完整重启 MaiBot**。

## 故障排查

| 现象 | 原因与处置 |
|---|---|
| **同一条回复的内容被讲了两遍**（先出全文，再出后半段） | 宿主没有采纳改写。日志会同时出现「未能就地改写宿主共享对象」与「实发校验未通过」。把 `splitter.diagnose_payload` 设为 `true`，回传日志里的 `含长文本的字段` 与实际样本长度，确定宿主到底读哪个字段后修正回填位置 |
| 完全不切分，日志出现「尚未观测到 maisaka.replyer.after_response」 | 该 Host 版本的 replyer 钩子未派发。把 `splitter.scope` 改成 `all` 即可不依赖该标记 |
| 回复被切了两次 | 宿主 `[response_splitter] enable` 没关 |
| 日志出现「未能在出站载荷里定位正文，放弃切分」 | 该 Host 版本的出站载荷字段名不在预期列表内。把 `splitter.diagnose_payload` 设为 `true`，回传日志里的 `kwargs键` / `message键` |
| 命令回执被切分 | `scope` 为 `all` 时回执也会成为候选；保持在 `replyer_only`，或确认命令保护窗口生效 |
| 补发内容被再次切分 | 重入保护失效，检查日志是否有「补发任务」相关异常 |
| `[E_CAPABILITY_DENIED] 未获授权能力: xxx` | manifest 漏声明能力 → 补声明 + 完整重启 |
| `插件配置版本非法: 缺少 plugin.config_version` | 配置模型缺 `config_version` |
| TOML `Invalid statement (at line 1, column 1)` | `config.toml` 带 UTF-8 BOM，用无 BOM 方式重写 |
| 改了代码不生效 | 依赖模块命中 `sys.modules` 缓存 → 完整重启 MaiBot |

## 开发

```bash
python check_plugin.py --plugin .        # 结构自检（零依赖，随插件分发）
python tests/smoke_test.py               # 冒烟（需 maibot-plugin-sdk，缺失则 SKIP）
python -m pytest tests/ -v               # 规则引擎 + 审计用例
```

交付门禁 `run_gates.py` **不在本插件目录**（它属于 devkit，未随插件分发），
需要从工具链目录调用：

```bash
python <devkit 目录>/run_gates.py --plugin <本插件目录>
```

> 注：README 早期版本把 `run_gates.py` 写成可直接在插件目录执行，那是错的——
> 该脚本并不存在于插件目录内。审计时按「文档承诺的命令能不能真的跑起来」逐条核对才发现。

测试要点：

- 规则引擎的四个不变量在每条用例都要成立：**零内容丢失**、**保护区完好**、
  **段数不超上限**、**不产生空段**。
- 冒烟测试会断言**每个装饰器紧贴的 def 名**（装饰器与 def 之间插入辅助方法会
  静默把组件注册到错误的函数上，本地全绿但真机报 `unexpected keyword argument`）。
